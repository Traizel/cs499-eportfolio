Professional growth and direction

My computer science coursework and this capstone have helped me develop a more disciplined approach to software development. I can take an existing program, identify weaknesses in its design, make a focused improvement, and support the result with code and tests. My strongest interests are backend and full stack development, where application structure, data access, and clear interfaces directly affect the user experience. This portfolio shows how I approach those responsibilities and how I explain the limits of my work.

Courses across the program gave me different ways to evaluate a system. In CS 340, I worked with Python and MongoDB to support animal shelter records. In CS 350, the thermostat connected software decisions to sensors, buttons, a display, and serial communication. Full stack coursework helped me think about how a user interface depends on application and database behavior, while secure coding coursework reinforced the need to consider invalid input and failure paths early. Revisiting earlier work during CS 499 made these connections concrete. A program that completes its main task still needs understandable boundaries, controlled failures, and evidence that its behavior is correct.

My professional goal is to contribute to applications that other developers can maintain and users can depend on. The capstone strengthened my ability to explain why a change is worthwhile, recognize compatibility costs, and separate a measured result from an assumption. These habits prepare me to discuss my work in a technical interview and to take responsibility for changes in a shared codebase.

Collaboration and communication

The capstone artifacts were developed as individual coursework. I support collaboration by making decisions and review evidence available to other people: the portfolio includes the original source, enhanced source, a code review video, written narratives, runnable tests, and instructions. The review guide records specific final checks and their resolutions. For example, the thermostat narrative named baseline files that were not in the submitted archive; the final version now points to the actual original/Thermostat.py file. Documenting that correction gives a reviewer a consistent starting point for comparing the work.

In a team environment, I would use a review request that states the problem, proposed change, expected behavior, and test evidence. Reviewers should be able to question a decision and receive a response tied to the code or a requirement. Written notes and a walkthrough offer different ways to participate. For the animal shelter application, a rescue coordinator would need an explanation of candidate filters and their limits, while a developer would need the accepted input fields and result types. A database administrator would need the index definition and required permissions. Giving each audience relevant information supports a shared decision about what the system should do.

The code review video and narratives also helped me practice explaining technical choices at different levels of detail. I can describe the purpose of separating service logic from database access before discussing repository interfaces. I can explain that a thermostat should avoid repeated changes near its target before showing the hysteresis thresholds. This approach supports both collaboration and professional communication without requiring every reader to have the same technical background.

Software design and algorithmic judgment

The software engineering enhancement demonstrates my ability to improve maintainability through responsibility boundaries. The original AnimalShelter class combined connection setup with CRUD operations. The enhanced package separates configuration, validation, service behavior, repository access, results, and errors. Injecting a repository makes it possible to check service behavior without a database. Typed results distinguish an unchanged record from a missing record, and controlled errors distinguish a failed query from an empty result. The 31-test offline suite provides evidence for these behaviors.

The thermostat enhancement demonstrates how I select data structures for a specific problem. A min heap orders recurring work by monotonic deadlines, and a bounded deque with a rolling sum calculates a moving average. Updating the average takes constant time, while removing and reinserting a scheduled task takes logarithmic time in the number of tasks. The value of the heap here is explicit, independently scheduled work; the original small set of counters already had constant work per iteration. I do not claim a hardware speed improvement from the simulation.

These changes also required tradeoffs. Averaging readings reduces short fluctuations but delays the response to a sudden change. Hysteresis stabilizes the indicator behavior near the setpoint, while a bounded command queue prevents button input from growing without limit. A cooperative scheduler can still be delayed by a slow hardware operation. The 19-test suite and virtual simulation let me evaluate scheduling, thresholds, fault recovery, and cleanup before testing the physical circuit.

Database work and security

The database enhancement builds on the same AnimalShelter architecture and adds validated search, bounded pagination, projection, aggregation, and a compound index. This progression shows how software design enables a later capability without mixing all responsibilities into one class. The supplied live verification used 10,000 generated records and returned the same 100 candidate records before and after indexing. Documents examined fell from 10,000 to 100 for that workload. I treat this as evidence for one query pattern, with the generated data and measurement limits stated beside the result.

Security is part of the design of these interfaces. The animal shelter service accepts approved fields and scalar values instead of arbitrary caller-supplied database operators. Updates and deletes target a unique record identifier. Configuration is separate from the source, and error handling avoids passing driver details to callers. In the thermostat, invalid or nonfinite readings trigger a fault state, clear the sample history, disable indicators, and suppress invalid serial output. These decisions reduce specific failure and misuse risks.

The boundaries of those protections matter. Application validation does not replace database authentication, authorization, or deployment controls. The database package does not configure server roles, and index administration should use permissions appropriate to that task. The thermostat is a coursework prototype that still needs physical integration testing. Identifying these limits helps me choose the next validation step and communicate responsibly with the people who would deploy or maintain the software.

How the portfolio fits together

The portfolio follows a progression from reviewing existing work to explaining and verifying improvements. The code review introduces the original behavior and planned enhancements. The software engineering category shows the AnimalShelter redesign; the algorithms category shows scheduling and control logic in the thermostat; and the database category extends the AnimalShelter package with search and analysis. Each category includes an original artifact, enhanced code, a narrative, and evidence so the reader can connect a claim to its implementation.

Together, these materials address the five program outcomes through documented review strategies, oral and written communication, evaluation of design tradeoffs, working software, and explicit security controls. The outcome map provides specific places to inspect each area. The final offline verification passed 31 software engineering tests, 19 thermostat tests, and 45 database-package tests; the database suite includes the earlier 31 tests. The live MongoDB evidence is retained from Milestone Four, and the hardware work remains a separate validation step. My next areas for growth are representative database workloads, deeper deployment security checks, physical device testing, and incorporating reviewer feedback into future revisions.
